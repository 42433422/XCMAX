4. 任务执行完整调用链与三个场景核验

4.1 FHD 持久任务主链

POST /api/agent/tasks → requireagentprincipal / authenticatedruntimecontext → createunifiedtask → 构造/接管 PlanGraph → starttaskfromplan → waitinguser → 参数指纹绑定的 approval grant → approveandenqueue 同事务消费授权和写 execution → AgentTaskDispatcher.claim → workerclaimscope / ClaimedRunRepository → executedispatchedrun → executeready_steps → executestep → AgentToolExecutor.execute → tools facade → 宿主业务或 Mod → 结构化结果/业务 harness → 保存 AgentRun 和 Task 投影 → 轮询/SSE 返回。S04S05S06S07S08S09S10S61

主 Run 有 planning、running、retrying、waiting_user、paused、blocked、completed、failed、cancelled 等状态；队列另有 queued/claimed 状态。暂停/取消是协作检查，不能强行终止正在执行的同步工具，也不能撤销已发生的业务写入。已运行非幂等步骤的租约过期会 blocked 并要求对账；这是主链值得保留的保证。相同保证不能推及员工直接执行和远端 incident 恢复。S10S11

6. 最严重的技术问题

6.1 高危安全边界

工作区不是可靠的执行隔离边界。 本次只用临时哨兵文件，在不修改源码的情况下验证：readonly 的普通文件读取可以通过工作区符号链接读到工作区外；写模式的 Python 工具可以读取/修改工作区外的临时文件，子进程继承服务进程的操作系统用户权限。S17S18

该问题有认证、员工 entitlement、manifest 写权限/风险 gate 等前提；默认 readonly 确实阻止 Python 工具。它不是已证明的匿名远程攻击，也不证明生产以 root 运行或已发生真实跨企业泄露。若服务用户可读写密钥、其他租户数据或业务目录，这条边界缺陷的后果符合 P0，因此按 P0 条件高危 优先处理。

另外，FHD 员工工具允许列表没有在最终 dispatch 强制执行，compose_gates 对授权异常继续放行；EmployeeRunLog 的共库跨租户摘要返回已用真实 SQLAlchemy 过滤器和临时两租户数据复现。后两项按 P1 处理，真实 HTTP/部署权限影响范围须在修复验收中确认，不能夸大成全库数据已经暴露。S12S13S14S16S66

6.2 最大的系统性风险：跨层没有一致的执行事实

“已受理”“结果未知”“执行失败”“验证了某一个修复版本”没有被所有层共同保存和解释。外层重试能丢弃内层要求核对的原任务身份；执行失败能被 DAG 记为成功；旧验证可替新修复背书。这三类错误组合，比缺少一个新的模型或调度算法更影响企业业务可信度。S24S25S33

6.3 已识别的业务状态不一致路径

以下是本次覆盖中发现的高风险路径清单，不声称穷尽仓库所有可能性：

  1. 已 POST/已受理 → timeout/poll_failed → 内层要求核对 → 外层分类重试 → 新请求缺旧 task ID：可能重复执行或错误权限失败。
  2. 普通 Para 路由发现旧 CLI 日志 → 换工具并移除 task ID：原任务未知时可能重派。
  3. unknown 未进入 pending completion 扫描 → 原任务迟到结果无法按同一身份收敛 → 长期处理中或假失败。
  4. 同进程重复 claim、活任务 180 秒后被抢、无 CAS/续约 → 两个拥有者可能同时派单。
  5. outbox 两 drainer 发送同 ID；incident 指纹 query-then-insert 缺唯一门槛 → 并发去重并非持久保证。at-least-once 本身正常，风险在消费者副作用幂等不足。
  6. incident 已提交 → daemon thread 尚未派发就崩溃；或远端已受理 → team claim 尚未落库就崩溃：可能丢派或恢复重派。
  7. 条件边在 PlanGraph→AgentStep 转换丢失 → 互斥分支都执行；合法 DAG 因列表顺序阻塞、空计划残留 error 却 completed。
  8. DutyGraph 员工返回 handler_failed → 节点 success → 依赖继续 → run completed；动态 DAG 则可整体失败但下游副作用已执行。
  9. 传统节点图达到访问/循环上限 → 只产生 warning → API 丢弃 warning 并存 completed。
  10. fix 重试产生新结果 → 原 verify=true 被复用 → team_succeeded 使用过期证据。
  11. 本地员工修正参数并成功 → 历史失败仍污染终态 → 直接入口不看 nonretryable 整任务重跑。
  12. error-only/空 webhook/某个辅助 handler 成功 → 较宽松入口视为完成；工单严格合同另行拒绝，造成不同视图不一致。
  13. 同步工具未执行 deadline → worker 仍心跳续租 → 任务永久占槽，协作取消无法落实。
  14. SQL 初始化失败且企业部署未设置 require durable → 内存 run/queue 降级接单 → 重启可能丢状态；线上是否发生 U。
  15. 多设备计划中一台受理、一台拒绝 → 响应忽略失败分支 → 调用方误以为任务集合完整。S01S11S15S24S25S27S28S29S31S32S33S34S35S36S40

8. 当前工程成熟度

整体 L2：功能可用；具备局部 L3：可重复验证的事务、领取、审批和有限恢复机制。

  • 高于 L1 的依据：存在真实多步计划、依赖调度、工具执行、数据库状态、审批、预算、轮询恢复和部署；并有当前 SHA 的真实数据库测试。
  • 尚不能整体 L3：同计划/失败结果跨入口不一致；真实客户、真实执行器故障恢复和完整交付的当前 SHA 证据不齐；局部反例影响可重复业务交付。
  • 尚不能 L4：P0 条件高危和多项 P1 未清，跨进程拥有者/未知结果/完成证据尚未闭合，缺代表性长期生产可靠性与安全隔离验收。
  • 不评 L5：未建立大规模容量和多租户负载证据，也没有必要在当前阶段追求该标签。

距离下一层 L3 的关键，是先让相同输入在所有允许入口得到同一计划与完成语义，再在固定发布 SHA、受控企业测试租户和真实执行器上重复完成三个业务场景，包含失败与恢复。

9. 生产环境可靠性判断

现有证据支持“服务已部署、部分业务机制能运行”，不支持“当前主分支已具备企业关键业务无人值守的生产可靠性”。

Issue #2424 的 scheduler runtime 报告从 3 个异常作业减少到 1 个，但 2026-10-19 21:31 UTC 的评论仍报告 runtime_healthy=false；watchdog 作业成功表示检查执行成功，不是调度器健康。公开健康接口 200 与内部作业不健康可以同时成立，根因本次未验证。https://github.com/42433422/XCMAX/issues/2424#issuecomment-6277784572

落盘生产 SLO 报告显示 sourceunavailable、ConnectionResetError、coverage=0、day0eligible=false、读数缺失。因此没有足够连续观测证明生产 SLO；这不表示实际可用性为 0% 或故障率为 100%。规则模式 benchmark 也明确 llm_verified=false，不能拿它证明真实模型任务成功率。S46S47

部署过的旧 SHA、安装更新生命周期通过、主分支静态实现和 CI 事务通过应各归其位。真实发布与灾备同步日志值得承认，但不替代订单/采购/客服原问题的业务验收。对读操作、文档辅助、有人复核的受控试点，可以在限制有缺陷入口及完成最小整改后继续交付；财务、采购、跨企业管理和自动代码执行等重要写操作不宜在当前状态下承诺无人盯守。

10.2 最小必要整改集合

不要求立即合并全部引擎或迁移到 Temporal。先利用现有模块完成以下最小闭环：

  1. 安全收口：暂时禁用没有 OS 隔离的 Python 写执行；修符号链接边界、工具最终白名单、授权异常拒绝及日志租户筛选。每条策略都要有拒绝路径回归。
  2. 统一事实合同：跨层传 businesseventid、tenant/user、task_id、attempt/revision、accepted/unknown/terminal、必需子任务和验证产物身份。先采用一个共享类型与适配器，不重写业务 Mod。
  3. 禁止盲目重放：unknown 纳入同任务号 reconcile；补原子 claim/续约/fencing 和入站唯一消费；任何新修复使旧 verify 失效；非幂等/不可重试任务不整段重跑。
  4. 修正执行语义：修条件与依赖失败传播、循环上限终态；正式支持的入口共用语义测试。短期可明确拒绝尚不能正确执行的图，而不是静默执行不同语义。
  5. 可靠性门禁：企业模式 SQL 失败不接持久任务；不能有界终止的工具暂不进入自主写路径；完成窄范围真实业务与故障恢复验收。

12. 最终独立审计结论

XCMAX 不是只有若干 AI API 调用和条件分支的薄包装。它已有真实任务计划、多步执行、业务工具/Mod 接入、员工协作、持久状态、审批、限额和部分故障恢复。与此同时，它没有形成所有关键入口共同遵守的企业级执行协议；计划语义、拥有者、未知结果、失败传播和独立核验仍存在已复现的缺陷。部署、测试与文档的数量不能弥补这些正确性问题。

第一：是否真正拥有完整的 AI 任务编排与执行引擎？

拥有实质性的任务编排与执行系统；尚未拥有经证明完整、统一、可靠的企业级自主执行引擎。 “有引擎”成立，“完整无人值守企业闭环已成立”不成立。准确归类是用户给出的第二档：具备一定容错能力的 Agent 执行系统。

业务任务、工具/Mod 合同、审批、持久状态与实际交付的连接。 具体是 FHD agent_orchestrator 的受控业务执行内核，以及可抽取复用的 durable attempt/reconcile 与客户验收合同。这些比单独的 LLM prompt、HTTP proxy 或 Grok Bot/Dot 名称更有保留价值。当前通用编排算法的独特性不足以认定强技术壁垒；形成壁垒需要跨行业稳定合同、真实失败数据和长期可重复交付证据。

第三：目前最危险的架构问题是什么？

跨层没有一致的执行身份与事实，导致“结果未知被重派、失败被当成功、旧验证背书新执行”。 安全方面另有必须优先处理的工作区隔离和员工权限边界缺陷；这两类问题均不能通过换模型解决。

第四：距离成熟企业级核心引擎还有多远？

不是从零开始，也不是一次小修即可完成。 完整保留并修复已审能力、补关键受控验收约需 412–792 人时，并需要真实执行器、企业测试租户、发布身份和长期运行证据。达到 L3 的条件比 L4 少；没有后三类证据，不能靠静态评分跨级。

第五：如果只能保留一个核心技术模块，是否应保留这个引擎？

倾向保留，但应明确保留边界：选择 FHD/app/application/agent_orchestrator 及其必要的工具合同、审批和持久化接缝，作为业务执行核心。 这是对可复用工程资产的判断，不是宣称它已生产合格。把 Para/Grok/Dot 留作适配器，把 Mac Control 已有的 attempt/reconcile 机制逐步用于高风险远端执行；没有必要把所有重复 runtime 和不一致旁路一起定义成必须保留的“核心”。

1. 结论及证据边界

MODstore 已实现真实的任务路由、按依赖分层的线程池调度、三角色 incident team、Para HTTP 调用与轮询、工单完成契约、部分 SQL outbox、部分任务状态持久化，以及默认关闭的 Mac Control 持久执行通道。它超过单纯 AI API 包装的范围。

但是，这些执行通道没有共享一致的“已受理、结果未知、失败、已验证成功”契约。本次在隔离环境复现了：已受理且要求核对的 Para 任务仍被外层恢复循环重新提交给员工执行器；依赖 DAG 将员工明确返回的执行失败保存为成功；恢复后的 fix 复用前一次 verify；节点图因循环被强制中止仍被实际 API 保存为 completed。它们直接影响核心正确性，因此当前代码不能支撑“无人持续盯守、关键业务可靠闭环”的企业生产承诺。

本报告严格区分：

  • 实测：运行固定 SHA 的真实函数、SQLAlchemy SQLite 数据表及实际 API 函数，使用模拟 HTTP/员工执行替代外部副作用。实测说明本地代码分支和状态写入行为成立，不能证明实际生产已经造成重复业务操作。
  • 静态：从当前源码可达路径得出的设计/缺陷判断，注明触发条件。
  • 未验证：真实 Para/devfleet-private 服务、Grok Bot/Dot 执行器进程、Redis 多节点、实际客户业务结果及部署配置。仓库中的客户端实现不能代替这些服务的运行证据。

9. 对总报告评分与成熟度的建议

仅此MODstore执行链建议“执行器调度与容错”约5–7/15、“状态一致性”约4–6/15。原因是已有分层并行、事务outbox、严格客服完成合同和可选强持久通道可得分，同时E01–E07涉及正确性基础，应显著扣分；未知生产容量和外部Para能力不直接等同缺陷，而降低证据覆盖与置信度。应由主审结合FHD和安全实审统一八项得分，避免子模块成绩机械相加。

当前更接近L2功能可用，含若干L3局部机制：确有执行和恢复功能，但跨入口契约与重启/未知结果安全性未形成可重复验收。修复最小集合并在固定SHA上通过多进程和真实执行器验收，可合理目标L3；达到L4还需要安全隔离、可观测SLO、部署回滚和客户业务一致性的独立证据。
