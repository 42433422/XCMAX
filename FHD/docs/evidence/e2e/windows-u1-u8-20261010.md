## U8 明细

### 出单

- `POST /api/business/shipment/create`（客户B / A 产品 ×10 / 单价 100）：HTTP 200，发布了 `shipment.created` 事件
- 出货记录读回 1 条，金额 1000，状态 pending
- 出货记录导出 Excel：`GET /api/shipment/shipment-records/export` 返回 HTTP 200，文件为 xlsx，5,148 字节
- **发货单 Excel 生成失败**：`POST /api/shipment/generate` 返回 HTTP 403，消息是「该旧业务接口尚未提供安全的租户数据隔离」。企业租户会话下拿不到发货单文件，内置模板有 11 个

### 销售到收款（产品标准路径：对话 → 确认 → 审批）

1. 对话发送「把 A 产品卖给客户B，10 个，单价 100，开票收款」，系统生成计划 `sales.execute_closed_loop`。回复「确认」后，生成一笔审批请求。
2. 第一次批准返回 HTTP 409「审批通过后 AI 工作流执行失败，审批已取消」。后端报 `sqlite3.OperationalError: no such column: customers.credit_limit`，出错位置是 `_closed_loop_resolve_customer`。
3. 同一个库上，`GET /api/finance/receivables` 和 `GET /api/finance/transactions` 都返回 HTTP 500，报 `no such column: financial_transactions.journal_entry_id`。

**根因（只读比对客户库和全新首启库）**：两边的 alembic 版本相同，都是 `2026_09_27_tenant_rbac_owner`，但客户库缺少以下列：

| 表 | 客户库缺失的列 |
| --- | --- |
| customers | `credit_limit`、`credit_used`、`is_credit_limited` |
| financial_transactions | `journal_entry_id` |

`customers.credit_limit` 只出现在已归档的 baseline 前迁移（`_archive_pre_baseline_2026_06_22/xcagi_v4_inventory_purchase.py`）里。`financial_transactions.journal_entry_id` 没有任何迁移会添加。新装库由 ORM 建表，所以有这些列。从旧版升级上来的库被标记为 head，但一直没有补上这些列。结果是升级客户的销售闭环、收款和财务列表全部失败，新装客户不受影响。

**诊断复测（只在隔离副本上做）**：

- 按全新库的列定义补了 4 列，财务两个接口恢复为 HTTP 200
- 再次批准失败，原因是「当前租户下无可用仓库」。客户库和全新库的 warehouses 都是 0 行。闭环发货要求当前租户至少有一个 active 仓库，并且该仓库里有对应产品的库存台账；只填产品的 quantity 不算库存
- 建了仓库 `WH-U8`，入库 100 后再走一遍对话、确认、批准，HTTP 200，审批状态 approved：
  - 销售订单 `CL1-5bec70815edf1149`：confirmed / invoiced / **paid**，total 1000，paid 1000
  - 明细 1 行：A 产品 ×10，delivered 10
  - 库存事务：in 100（0→100），out −10（100→90，引用 sale_delivery）
  - 记账：`销售开票-订单1` 与 `收款-订单1` 两张凭证，均为 posted，借贷各 1000
  - 收款核销：receivable_allocations 1 行，status paid，amount 1000
  - 重启后上述数据仍在
- 观察到两处不一致：产品表的 `quantity` 字段仍是 100，与库存台账的 90 不一致；`/api/finance/receivables` 只列手工凭证，这笔已核销的销售收款不显示

### 结论

U8 判 FAIL。在真实升级的客户库上，「出单 → 收款」走不通，有三处阻断：

1. 升级库缺列。销售闭环和财务接口在升级库上直接报错，这是主要阻断。
2. 新租户没有默认仓库，闭环发货无法执行。
3. 发货单 Excel 生成在企业租户下被 403 拦截。

9-28 那轮 U8 的失败原因没有留下记录，所以无法确认是否与第 1 条相同。如果那台机器的库也是从旧版升级上来的，第 1 条就可能是同一原因。

建议修复：

- 新增一个幂等迁移，按 inspector 判断列是否存在，补齐上述 4 列，并在 CI 中对比「升级库 vs 新装库」的表结构
- 首次进入 ERP 时创建租户默认仓库，或者在闭环失败时提示用户先建仓库
- 为 `/api/shipment/generate` 补上租户隔离，然后放开该接口
