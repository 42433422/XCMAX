# 历史凭据泄露事件处置与发布解锁手册（流程 SSOT）

> 适用事件：`.github/security/credential-incidents.json` 中的 MIMO / QQ Bot / SMTP 三项历史事件。  
> QQ Bot：产品功能已从代码删除；收口动作只剩控制台作废旧密钥（见下表）。  
> **当前状态：尚未完成供应商侧撤销、轮换及旧凭据拒绝验证。** 不得把本手册、PR、CI 通过、`accepted_risk` 或代码删除视为已完成处置。  
> 执行者：具备相应服务商后台与生产密钥管理权限的账号所有者/授权运维。复核者必须独立于执行者。

## 1. 立即控制范围（P0）

1. 在受控的私有工单中记录事件编号、服务商账号/应用标识、业务负责人和执行人；**不粘贴密钥明文、SMTP 密码、OAuth token、邮件头、客户数据或完整含凭据 URL**。不要在公开 GitHub Issue、PR、Actions 日志、聊天、截图或附件中放入这些信息。
2. 从服务商后台检查该密钥是否仍存在及其权限；审阅可用的调用日志、异常流量、账单、发信记录和机器人消息。无法查询时记录“未知”，不能记为“未被使用”。
3. 先评估是否需要短时间停用相关功能，并准备安全替换凭据，避免撤销后服务误恢复到硬编码/旧环境值。影响客户业务的操作依照既有变更审批。
4. 核对可能持有旧凭据的服务器变量、CI 秘密、桌面包、配置文件、镜像、备份、Git 历史和历史外链；仅在授权范围内排查。**源代码移除并不会令历史泄露的凭据自动失效。**

## 2. 三项必须执行的供应商侧动作

| 事件 ID | 服务商/对象 | 执行动作 | 复核重点 |
| --- | --- | --- | --- |
| `INC-20260905-MIMO-API-KEY` | MIMO 模型 API 凭据 | 生成权限最小化的新 Key，部署到受控凭据存储后撤销旧 Key | 旧 Key 无法调用；新 Key 可完成最小健康检查；账单/异常调用已核查 |
| `INC-20260905-QQ-BOT-CREDENTIALS` | QQ Bot 机器人应用凭据（**功能已代码下线**） | 在 q.qq.com 控制台作废/删除机器人旧 AppSecret 与 Token；服务端不再挂载 QQ 桥接 | 控制台侧旧凭据已作废；仓库无 QQ Bot 运行时路径 |
| `INC-20260905-SMTP-CREDENTIAL` | SMTP/邮件服务凭据 | 撤销/重置旧授权码、密码或应用专用令牌，替换发信服务配置 | 旧凭据 SMTP AUTH 被拒绝；新凭据最小受控投递成功；异常发信/登录已核查 |

**顺序**：在供应商支持并行凭据时，先建立最小权限新凭据并完成配置/回滚准备，再禁用旧凭据；如无法并行则优先阻断旧凭据并在维护窗口恢复服务。不要为了测试将旧密钥写回仓库。不要发送真实客户邮件或修改客户业务数据做验证。

## 3. 旧凭据失效和服务恢复验收

- 先核对供应商后台撤销状态，再由授权运维在**受控环境**执行一次最小、无业务副作用的旧凭据认证尝试，确认返回明确的认证拒绝（不是网络超时、服务不可用、参数错误或限流）。后台显示停用不能替代旧凭据拒绝验证；无法安全复测时保持未解决并请求供应商协助。
- 独立验证新凭据与受影响业务功能正常；对异常费用、发送行为和访问日志作出明确结论或保留未查清项。
- 逐个事件生成**不含敏感值的私有证据包**：操作者和独立复核者身份、服务商/账号的非敏感标识、撤销和轮换时间、旧凭据拒绝时间及结果、新凭据健康检查结果、最小化日志、变更/审批编号、证据 SHA-256；保留原始证据于限制访问的私有位置，公开仓库仅登记不可逆哈希与必要时间。
- 如果发现异常使用、数据访问或费用，按安全事件流程扩大影响面核查；不能仅凭“Key 已换”就宣布不存在客户数据影响。

## 4. 更新事件登记与门禁

本仓库的权威登记位于 `.github/security/credential-incidents.json`。完成**真实**服务商侧操作及独立复核之后，逐条填写/复核（不要批量伪造）：

- `status: resolved`；
- `revoked_at`、`rotated_at`、`old_credential_rejected_at`：使用真实且带时区的操作/验证时间；
- `required_actions` 至少含 `revoke`、`rotate`、`verify_old_credential_rejected`，并提供匹配的实际完成记录；
- `author` 为实际执行者，独立 `reviewer` 不得与其相同；填写 `reviewed_at`、有边界的 `review_due` 与有效的 `resolution_evidence_sha256`。撤销和轮换均须不晚于旧凭据拒绝验证，验证不晚于复核，复核不得在未来且复核期限未过。以 `FHD/scripts/security/normalize_security_report.py` 的 `_credential_resolution_is_valid` 当前契约为准，若证据不满足其校验就继续保持未解决。

**禁止**：直接将 `accepted_risk` 改成 `resolved`、编造时间或哈希、填入新旧密钥正文、添加忽略/豁免规则、屏蔽扫描器或削弱发布门禁。

完成后，针对最终 **main 的精确 SHA** 重跑 `Security full release scan`，检查其 `credential-rotation`、`gitleaks`、`codeql` 与总门禁的完整结果。**仅在所有阻断项清零、报告新鲜且完整、真实客户端/生产功能回归通过后**，才讨论正常发布流程；一般 PR 的 `gitleaks` 绿色不代表全历史和凭据事故门禁绿色。

## 5. 回滚与未完成状态

供应商撤销通常不可逆，回滚应仅切换至**另一组新生成且受控的有效凭据**，不得恢复旧泄露密钥。若新凭据验证失败，应保持相关服务受控降级，并保留原事故未解决状态。此文档的合入不意味着已撤钥、已轮换、已清理 Git 历史、已部署或已解除发布阻断。
