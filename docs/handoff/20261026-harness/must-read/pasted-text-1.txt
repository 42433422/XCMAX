下面的清单是整改与验收待办，不是 76 个已经确认存在的缺陷。每项标注：

- 已发现： 源码直接显示的不一致或风险。
- 待验证： 已有相关实现，但缺少足够的实际运行证据。
- 增强： 为达到目标架构而新增或提升的能力。

## 一、P0：身份权限与安全边界（10项）

SEC-01 · 统一工具入口身份认证

已发现

/api/tools/execute 不能再以请求头或请求体中的 user_id 作为可信身份；改为经验证的 Principal

SEC-02 · 统一客户租户隔离

待验证

聊天、工具、后台任务、数据库、缓存、记忆全部采用同一可信 tenant_id

SEC-03 · 统一 Mod 权限校验

待验证

每次工具调用均检查 Mod 授权，禁止越权使用其他 Mod 能力

SEC-04 · 统一 RBAC 权限控制

待验证

客户、企业管理员、开发者、系统员工按动作级权限分离

SEC-05 · 统一高风险操作审批

待验证

数据库修改、文件覆盖、删除、部署等操作必须先授权后执行

SEC-06 · 审批凭证绑定原任务

待验证

审批必须绑定 run_id、step_id、参数摘要、操作者及有效期

SEC-07 · 防止重复业务写入

待验证

断线、超时、重试后不得重复创建订单或库存记录

SEC-08 · 不可信内容与指令隔离

待验证

用户文件、网页、工具输出及 RAG 内容不能覆盖系统规则或提升权限

SEC-09 · 危险工具默认拒绝

增强

Shell、文件系统、网络、数据库操作按明确能力清单和工作区边界执行

SEC-10 · 工具调用审计与脱敏

待验证

完整记录调用身份、权限决策、结果；日志不得泄露凭据或敏感业务数据

P0 通过标准： 未授权执行、跨租户数据访问、未经批准的高风险写入、重复业务副作用均为 0。尤其 SEC-01 已确认存在身份信任边界不一致，但还需独立安全测试确定是否可被利用。

## 三、P1：工具调用系统（12项）

TOOL-01 · 统一 ToolSpec V2

待验证

所有工具拥有明确的名称、版本、参数、输出、风险、权限、成本和超时契约

TOOL-02 · 严格校验 JSON 参数

已发现

Legacy Chat 中无效 JSON 不得自动转换为 {} 后继续执行

TOOL-03 · 完善嵌套 Schema 校验

已发现

数组、嵌套对象、字段边界、枚举、额外字段都应严格验证

TOOL-04 · 统一工具执行器

增强

所有模型工具调用最终经过同一个受控 ToolExecutor

TOOL-05 · 统一结果回执

增强

必须明确区分 success、failure、pending、unknown 和 waiting_approval

TOOL-06 · 实现结果真实性核验

增强

写操作需要数据库主键、版本或读回证据；不能只依赖模型描述

TOOL-07 · 统一工具超时机制

待验证

每个工具有实际可执行的 deadline，超时不能被当作确定失败

TOOL-08 · 统一重试策略

待验证

仅可安全重试的工具自动重试；未知副作用先核对

TOOL-09 · 实现持久化幂等键

增强

同一 business_action_id 跨线程、进程、重启只能提交一次业务动作

TOOL-10 · 安全并行工具调用

已发现

根据只读性、幂等性、冲突域及依赖图决定是否并行，而非仅排除少数工具

TOOL-11 · 统一工具隔离机制

待验证

子进程、网络、文件系统及密钥访问均受明确的执行域限制

TOOL-12 · 支持动态工具发现与选择

增强

根据当前任务、行业 Mod、权限和能力相关性动态提供工具，降低误选

关键位置：`app/application/agent_orchestrator/tool_spec.py`、`tool_executor.py`、`app/legacy/chat/legacy_chat_adapter.py`。

## 四、P1：任务执行、状态与异常恢复（10项）

RUN-01 · 统一任务 ID

增强

每个真实执行任务关联稳定 run_id、每次工具调用关联 call_id

RUN-02 · 任务状态可靠持久化

待验证

步骤、依赖、审批状态、工具回执及最终产物重启后能够恢复

RUN-03 · 明确任务状态迁移

增强

禁止从 unknown、failed 等状态未经核对直接转为 completed

RUN-04 · 统一取消机制

已发现

流式请求取消或超时后，后台执行必须可协调停止或明确标记仍在运行

RUN-05 · 断点续跑

待验证

进程重启后从安全检查点继续，不重新执行已经提交的不可重复步骤

RUN-06 · 失败恢复与补偿

增强

支持失败定位、有限修复重试、业务补偿和人工接管

RUN-07 · 工具依赖图执行

增强

多工具任务采用 DAG，依赖顺序明确，失败时阻断下游

RUN-08 · 任务资源预算

待验证

限制模型调用、token、费用、工具执行次数和运行时间

RUN-09 · 执行结果独立验收

增强

模型认为完成不等于业务完成，必须由验证器与业务证据判定

RUN-10 · 任务完整生命周期查询

增强

用户可以查询开始、当前步骤、等待原因、执行结果及恢复建议

这部分应该优先复用现有 AgentOrchestrator 的运行记录、租约、状态和审批能力，而不是再开发第五套执行循环。

## 七、P3：第一梯队 Harness 增强能力（8项）

这些属于进阶目标，不应抢在 P0、P1 之前实施。

ADV-01 · 统一 Skills / MCP 接入

外部标准工具可以通过明确权限与工具协议进入执行体系

ADV-02 · 工具能力语义检索

面对大量工具，先召回任务相关的能力再交由模型选择

ADV-03 · 按任务选择执行策略

简单任务使用确定性工具路径，复杂任务使用规划与多轮 Agent

ADV-04 · Planner / Executor / Verifier 分工

规划、执行和核验角色职责分离，避免模型自己给自己的结果打分

ADV-05 · 多 Agent 协作调度

支持角色分工、依赖图、预算分配与统一结果汇总

ADV-06 · 工具调用策略自适应

依据错误类型、成本、任务复杂度和执行反馈调整计划

ADV-07 · 跨任务知识复用

使用经核验的业务经验改进后续工具选择和参数填写

ADV-08 · 运行轨迹回放与对照评测

可以复现历史任务，比较不同模型、提示词、工具版本的表现

## 八、实际验收与发布门禁（8项）

QA-01 · 真实模型工具调用评测

不能只用 Mock；至少覆盖模型实际选择工具、解析参数及反馈

QA-02 · 真实业务读写回读

订单、库存、客户等写入后检查数据库中真实记录

QA-03 · 连续任务 E2E

覆盖查询→新增→审批→修改→读回等多步骤链路

QA-04 · 安全攻击测试

跨账号、跨租户、越权、提示注入、参数篡改和重复请求

QA-05 · 故障注入测试

包括网络中断、模型超时、工具崩溃、进程重启、数据库暂时不可用

QA-06 · Windows/macOS 安装包实测

相同源码版本、真实安装环境、正常退出重开及恢复

QA-07 · 真实评价指标

工具选择准确率、任务完成率、错误写入率、P95 延迟和单任务成本

QA-08 · CI 与发布门禁

所有关键回归和真实验收证据绑定精确 SHA，失败不得标记生产就绪

## 九、建议分成 7 个实施 PR

| 批次   | 改造主题             | 对应任务       |
| ---- | ---------------- | ---------- |
| PR-A | 工具身份认证与安全边界      | SEC-01～10  |
| PR-B | 工具协议与执行器统一       | TOOL-01～12 |
| PR-C | 状态、幂等、取消和恢复      | RUN-01～10  |
| PR-D | 合并聊天与 Agent 执行架构 | ARCH-01～10 |
| PR-E | 上下文、记忆与智能交互      | CHAT-01～10 |
| PR-F | 追踪、性能与进阶能力       | OBS、ADV    |
| PR-G | 全量 E2E 与发布门禁     | QA-01～08   |

上述是逻辑实施批次，不要求每个批次只能有一个 GitHub PR。依赖关系复杂的部分应进一步拆成可独立测试、可安全回滚的小 PR。

其中最重要的一条约束是：不能通过简单让四个入口都调用一个包装函数，就宣称完成统一。必须证明它们经过相同的权限策略、工具契约、执行状态、结果核验和持久化机制。

## 十、最终合格标准

建议的正式验收目标

真实工具选择准确率

\>= 95%

端到端业务任务完成率

\>= 95%

未经授权工具执行

0 次

重复业务副作用

0 次

错误宣称业务完成

0 次

已完成任务重启后状态恢复

100%

跨账号或租户数据泄漏

0 次

这些是建议门槛，不是目前的实测成绩。P95 延迟与任务成本应先获取同硬件、同模型、同任务的基线，再制定合理阈值。

总计：76 项。 建议按 P0 安全边界 → P1 可靠工具调用和执行内核 → P2 智能对话体验 → P3 高级 Harness 能力推进。

当前 XCMAX 最需要做的，不是继续增加 AI 员工或工具数量，而是让用户从任何聊天入口发起任务，都能安全、正确、可恢复地执行，并拿到可核验的业务结果。

只有全部通过对应的实测门禁，才能将这些待办标为真正闭环。
